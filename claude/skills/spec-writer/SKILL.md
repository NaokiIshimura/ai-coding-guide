# 仕様書作成スキル

開発に必要な3つの仕様書を順番に作成し、開発の全体像を明確にします。

1. **requirements.md** - 要件定義書
2. **design.md** - 設計書
3. **tasks.md** - タスクリスト

## 重要な注意事項

- **仕様書の作成のみを担当**: コードの実装・修正は行わない。実装は仕様書作成後に `tasks-execute` スキルで行う
- **順序を守る**: requirements → design → tasks の順で作成し、各ドキュメントは前のドキュメントの内容を踏まえる
- **不明点の確認**: 不明点がある場合は、ユーザーに確認してから進める
- **既存ファイルは上書きしない**: 更新する場合も新しいタイムスタンプで別ファイルとして作成し、履歴を保持する
- **機密情報の保護**: パスワード、APIキー、トークンなどの機密情報は出力しない

## 入力情報

- **チケット番号 / 識別子**（任意）: JIRAチケット番号など
- **情報源**（呼び出し元から指定される。指定がなければ会話の内容から判断する）
  - 会話の内容（これまでの作業状況・調査結果）
  - JIRAチケット、GitHub Issue、markdownファイルなどから収集した情報
- **関連ファイル**: 参照すべき既存コードやドキュメント
- **制約事項**: 技術的制約やビジネス制約

## 実行手順

### Step 1: 準備

1. **識別子の決定**
   - チケット番号が与えられている場合はそれを使用
   - 与えられていない場合は、現在のgitブランチ名から推測（例: `ABC-123`, `feature/ABC-123` → `ABC-123`）
   - 推測できない場合は `tmp` を使用
2. **出力先ディレクトリを作成**
   ```bash
   mkdir -p .claude/plans/<識別子>/
   ```
3. **既存ドキュメントの確認**
   ```bash
   ls -t .claude/plans/<識別子>/ 2>/dev/null
   ```
   - 既存の requirements.md / design.md / tasks.md があれば、最新のものを読み込む

### Step 2: 情報収集

```
1. チケット/Issue情報の取得（呼び出し元で取得済みでなければ）
   ├─ JIRAチケット → atlassian-v2 MCP
   ├─ GitHub Issue → github MCP または gh コマンド
   └─ ユーザー要求 → 対話で確認

2. 既存コードの調査
   ├─ 関連ファイルの特定 → Glob, Grep
   ├─ 既存実装パターンの確認 → Read
   ├─ 依存関係の確認 → package.json など
   └─ 広範囲の探索 → Agent ツールで `Explore` エージェントを起動

3. 不明点の確認
   └─ ユーザーへの質問 → 明確化してから進める
```

### Step 3: requirements.md 作成

- テンプレート: `${CLAUDE_SKILL_DIR}/templates/requirements.md`（**作成前に必ず Read ツールで読み込み、その構成に従う**）
- 内容: 機能要件、非機能要件、ユースケース、受け入れ基準、制約事項

### Step 4: design.md 作成

requirements.md の内容を踏まえて設計を行います。

- テンプレート: `${CLAUDE_SKILL_DIR}/templates/design.md`（**作成前に必ず Read ツールで読み込み、その構成に従う**）
- 内容: システムアーキテクチャ、技術選定と理由、データモデル、API仕様、セキュリティ考慮事項、ファイル構成

### Step 5: tasks.md 作成

requirements.md と design.md の内容を踏まえてタスクを分解します。

- テンプレート: `${CLAUDE_SKILL_DIR}/templates/tasks.md`（**作成前に必ず Read ツールで読み込み、その構成に従う**）
- 内容: 優先順位付きタスクリスト、各タスクの説明、依存関係、推定工数・複雑度、完了条件
- タスクIDは `TASK-001` 形式、ステータスは 🔴 未着手 で作成する（`tasks-execute` スキルが進捗を更新する）

### 各ファイルの出力

各ファイルを作成する直前に日本時間のタイムスタンプを取得します。

```bash
TZ=Asia/Tokyo date +%Y_%m%d_%H%M_%S
```

### Step 6: 完了報告

1. 作成したファイルの一覧（パス）
2. 各ドキュメントの概要サマリー
3. 実装開始に向けた推奨事項（例: `/tasks.execute <tasks.mdのパス>` で実装を開始）

## 品質基準

### requirements.md

- [ ] 全ての機能要件が明確に定義されている
- [ ] 非機能要件（パフォーマンス、セキュリティ等）が網羅されている
- [ ] 受け入れ基準が具体的で検証可能である
- [ ] 制約事項が明記されている

### design.md

- [ ] アーキテクチャが要件を満たしている
- [ ] 技術選定の理由が記載されている
- [ ] データモデルが定義されている
- [ ] API仕様が詳細に記述されている
- [ ] セキュリティ考慮事項が含まれている

### tasks.md

- [ ] タスクが適切な粒度で分解されている
- [ ] 優先順位と依存関係が明記されている
- [ ] 推定工数が現実的である
- [ ] 各タスクに完了条件がある

## ファイル出力場所

```
.claude/plans/<チケット番号 or tmp>/
├── YYYY_MMDD_HHMM_SS_requirements.md  # 要件定義書
├── YYYY_MMDD_HHMM_SS_design.md        # 設計書
└── YYYY_MMDD_HHMM_SS_tasks.md         # タスクリスト
```

## 注意事項

- **一貫性**: 3つのドキュメント間で用語・ID等を統一する
- **トレーサビリティ**: 要件（FR-x）→ 設計 → タスク（TASK-xxx）の追跡可能性を確保する
- **参照**: 既存コードやドキュメントを必ず参照し、プロジェクトの慣習に従う
- **日本語**: 全てのドキュメントは日本語で記述する
- **空行**: ファイル末尾は必ず空行で終わる
